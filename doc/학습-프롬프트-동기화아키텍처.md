```

"북칸쇼"라는 독서 노트 앱이고, 데이터는 현재 브라우저 localStorage에만 저장돼.
처음에는 Supabase(서버)를 붙여 기기 간 자동 동기화를 만들 계획이었는데, 포기했어.
포기한 이유 중 하나가 "storage.js가 동기 함수인데 Supabase는 비동기라 충돌한다"는 거야.
이 말이 무슨 뜻인지, 그리고 어떻게 설계했다면 서버까지 갈 수 있었는지를 알고 싶어.

답할 때 지켜줬으면 하는 것:

- 설명 끝에 내가 이해했는지 확인할 질문 2개를 던져줘. 내가 답하면 채점해줘.
- 길이는 한 번에 소화 가능한 정도로. 너무 길면 끊어서 "더 볼래?" 하고 물어봐.
```

## ② 동기(synchronous)와 비동기(asynchronous) — 가장 먼저

```
프로그래밍에서 "동기"와 "비동기"가 뭔지 기초부터 알려줘.
나는 이 두 단어를 들었을 때 머릿속에 그림이 전혀 안 그려지는 상태야.

- 동기 코드가 실행되는 방식을 음식 주문에 비유해서 설명해줘.
  (줄 서서 기다리는 것과 어떤 점이 같은지)
- 비동기 코드가 실행되는 방식을 같은 비유로 설명해줘.
  (진동벨 받고 자리에서 기다리는 것과 어떤 점이 같은지)
- 자바스크립트(브라우저)에서 비동기가 왜 특히 많이 쓰이는지
  (왜 "기다리는 동안 다른 걸 못 하면 곤란한가")
- 아래 두 코드가 실행 순서에서 어떻게 다른지 설명해줘:

  // 동기
  const data = localStorage.getItem('key');
  console.log(data); // 여기는 언제 실행될까?

  // 비동기 (서버에서 가져오는 상황)
  fetch('/api/data').then(res => res.json()).then(data => {
    console.log(data); // 여기는 언제 실행될까?
  });
  console.log('이 줄은 언제 실행될까?');

- "이 코드가 블로킹(blocking)이다"와 "논블로킹(non-blocking)이다"가 무슨 뜻인지
- 비동기 코드를 다루는 세 가지 방식(콜백, Promise, async/await)이 무엇인지,
  같은 작업을 세 방식으로 쓰면 코드가 어떻게 다른지 나란히 보여줘
```

## ③ localStorage가 뭔지, 왜 동기인지

```
브라우저의 localStorage가 무엇인지 기초부터 알려줘.

- localStorage가 없던 시절에는 브라우저가 데이터를 어떻게 저장했는지
  (쿠키와의 차이도)
- localStorage가 실제로 어디에 저장되는 건지 (파일? 메모리?)
- getItem / setItem / removeItem 각각 무슨 일을 하는지
- localStorage가 동기 API인 이유 — 왜 await 없이 바로 값을 돌려줄 수 있는지
  (서버 호출과 근본적으로 뭐가 다른지)
- localStorage의 한계:
  - 용량 제한이 얼마이고, 넘으면 어떻게 되는지
  - 같은 기기의 다른 탭, 다른 기기, 다른 브라우저에서 보이는지
  - 브라우저가 멋대로 지울 수 있는지, 막는 방법(navigator.storage.persist)이 있는지
- sessionStorage와의 차이
- "localStorage는 서버가 없는 앱에서 어느 정도 규모까지 버틸 수 있는가"에 대한
  현실적인 평가를 해줘
```

## ④ 서버가 왜 비동기인가 — 네트워크 요청의 구조

```
"서버에 데이터를 저장하거나 가져오는 것"이 왜 비동기여야 하는지
아주 기초부터 설명해줘.

- 내 브라우저에서 서버까지 데이터가 오가는 과정을 단계별로 그려줘
  (요청 보내기 → 네트워크 이동 → 서버 처리 → 응답 → 내 화면)
- 이 과정에서 "기다리는 시간"이 어디서 얼마나 생기는지
- 그 기다리는 시간 동안 브라우저가 멈추면 어떤 일이 생기는지
  (왜 "화면이 굳는다"고 하는지)
- localStorage.getItem()은 왜 기다릴 필요가 없는지
  (서버 호출과 물리적으로 뭐가 다른지)
- fetch()가 반환하는 Promise가 정확히 뭔지 — "미래에 값을 줄 약속"이라는 비유로
- 아래 흐름에서 각 줄이 언제 실행되는지 순서를 매겨줘:

  console.log('A');
  fetch('https://example.com/data')
    .then(res => res.json())
    .then(data => console.log('B', data));
  console.log('C');

- 네트워크가 없을 때(오프라인) 서버 호출은 어떻게 되는지,
  localStorage 호출은 어떻게 되는지
```

## ⑤ 함수 설계: 동기 API vs 비동기 API

```
코드를 짤 때 함수를 동기로 만들지 비동기로 만들지 어떻게 결정하는지 알려줘.

- 함수 하나가 동기인지 비동기인지를 코드 모양만 보고 어떻게 구분하는지
  (return vs return Promise vs async 선언)
- 동기 함수 안에서 비동기 작업(fetch 같은 것)을 하려고 하면 어떤 일이 생기는지
  — 왜 "한 번 비동기는 영원히 비동기"라는 말이 나오는지
- 아래 두 버전의 함수가 있을 때, 이걸 사용하는 화면(컴포넌트) 코드가
  어떻게 달라지는지 보여줘:

  // 버전 A: localStorage 기반 (동기)
  function listBooks() {
    const data = JSON.parse(localStorage.getItem('books') || '[]');
    return data;
  }

  // 버전 B: 서버 기반 (비동기)
  async function listBooks() {
    const res = await fetch('/api/books');
    return res.json();
  }

- 버전 A를 쓰는 React 컴포넌트를 버전 B로 바꾸면 코드에서 뭐가 달라지는지
  (loading 상태, 에러 처리, useEffect 등)
- "화면 코드를 거의 안 바꾸고 데이터 계층만 바꾸는" 것이 가능한지,
  가능하다면 어떤 설계가 필요한지
```

## ⑥ Supabase가 뭔지 — 서버리스 백엔드의 개념

```
Supabase가 무엇인지 기초부터 알려줘.
나는 "서버"가 뭔지, "데이터베이스"가 뭔지 어렴풋이만 알고 있어.

- 예전에 서버를 직접 만들었을 때와 비교해서 Supabase 같은 BaaS(Backend as a Service)가
  뭘 대신 해주는지 (서버 코드 짜기, 배포, 인증, 보안 규칙 등)
- Supabase가 내부적으로 PostgreSQL 데이터베이스를 쓴다는 게 나한테 어떤 의미인지
  (localStorage의 JSON과 테이블의 차이)
- Supabase의 주요 기능 네 가지
  (Database, Auth, Realtime, Storage)가 각각 뭘 해결하는지 한 줄씩
- 내 앱에 Supabase를 붙이면 데이터 흐름이 어떻게 달라지는지 그려줘:
  지금: 앱 → localStorage
  Supabase 붙이면: 앱 → ? → Supabase → ?
- Supabase의 무료 플랜 제한이 뭔지 (개인 프로젝트에 현실적으로 어디서 막히는지)
- "RLS(Row Level Security)"가 뭔지, 왜 이게 없으면 위험한지 한 줄로
```

## ⑦ 로컬 우선(local-first) 아키텍처 — 핵심

```
"로컬 우선(local-first)" 아키텍처가 뭔지 알려줘.
이게 이번 주제에서 제일 이해하고 싶은 개념이야.

먼저 문제부터 정의해줘:
내 앱은 지금 localStorage에만 데이터가 있어. 오프라인에서 잘 돌아가고 코드도 단순해.
그런데 Supabase로 옮기면 오프라인이 안 되고 코드가 복잡해진다는 문제가 있어.
"로컬 우선"은 이 둘을 다 가지려는 시도라고 이해했는데, 맞는지 확인해줘.

그 다음:
- 로컬 우선의 핵심 아이디어를 딱 한 문장으로
- 데이터를 쓰고 읽는 흐름이 기존 서버 우선 방식과 어떻게 다른지
  아래 두 그림을 비교해줘:

  서버 우선: 앱 → (네트워크) → 서버 저장 → 앱에 응답
  로컬 우선: 앱 → ??? → ??? → 언젠가 서버에도 저장

- "낙관적 업데이트(optimistic update)"가 뭔지, 로컬 우선의 어디에 해당하는지
- 오프라인에서 데이터를 바꾸다가 나중에 온라인이 됐을 때 서버와 어떻게 맞추는지
  (이 과정을 "동기화"라고 부르는 이유)
- 로컬 우선을 구현한 유명한 앱들(Notion, Linear, Figma 같은 것)이
  이 문제를 어떻게 풀었는지 짧게

그리고 내 앱 상황에 적용해줘:
내 storage.js의 listBooks() 같은 함수는 동기이고 localStorage만 본다.
서버를 붙이되 이 함수들을 비동기로 바꾸지 않으려면 어떤 구조가 필요한지
다이어그램으로 그려줘.
```

## ⑧ 동기화 계층 분리 — "sync.js"를 따로 두는 이유

```
앱 코드와 서버 동기화 코드를 왜 분리하는지, 어떻게 분리하는지 알려줘.

- "계층(layer) 분리"라는 개념이 뭔지 — 왜 한 파일에 다 넣지 않는지
  (요리사와 배달부가 다른 사람인 것과 어떻게 같은지)
- 내 앱에서 만약 sync.js라는 파일을 따로 만든다면
  storage.js(로컬 담당)와 sync.js(서버 담당)가 각각 뭘 하고
  서로 어떻게 통신하는지 그려줘
- "변경 큐(change queue)"가 뭔지 — 오프라인일 때 한 작업을 어떻게 기억했다가
  온라인이 되면 서버에 보내는지
- 이 구조의 장점 두 가지:
  1. 화면 컴포넌트가 동기화를 전혀 몰라도 된다
  2. 나중에 Supabase를 다른 서버로 바꿀 때 storage.js는 손안 댄다
- 이 구조의 단점이나 어려운 점은 뭔지
- 실제로 이런 구조를 구현할 때 흔히 쓰는 도구나 라이브러리가 있는지
  (IndexedDB, Dexie.js, TanStack Query 오프라인 지원 같은 것)
```

## ⑨ 충돌 해결과 스키마 설계 — updated_at, deleted_at

```
기기 여러 개에서 같은 데이터를 바꿨을 때 충돌을 어떻게 해결하는지 알려줘.

먼저 문제 상황:
폰에서 문구 A의 메모를 "메모1"로 고쳤다.
맥에서 같은 문구 A의 메모를 "메모2"로 고쳤다.
두 기기가 동기화되면 어느 쪽을 믿어야 하는지 모른다.

이걸 풀기 위한 각 접근법을 설명해줘:

- 타임스탬프 기반 (updated_at): 마지막에 고친 쪽이 이긴다
  → 이 방법의 약점이 뭔지 (기기마다 시계가 다를 수 있다 등)
- soft delete란 뭔지 (deleted_at 필드로 삭제를 표시)
  → 왜 진짜 삭제를 하면 동기화에서 문제가 생기는지
  (내가 폰에서 지운 문구가 맥에서 합치기를 하면 돌아오는 현상이 왜 생기는지)
- CRDT(Conflict-free Replicated Data Type)가 뭔지 딱 한 단락으로
  → 타임스탬프 방식과 어떻게 다른지
- "최후 쓰기 우선(Last Write Wins)"이 뭔지, 언제 쓸만하고 언제 위험한지

그리고 내 앱의 현재 스키마에 비춰서:
- 책: id, title, author, created_at
- 문구: id, book_id, text, page, note, raw, position, created_at

Supabase 동기화를 위해 지금 당장 추가해야 할 필드 세 가지가 뭔지,
각각 왜 필요한지 설명해줘.
```

## 부록 — 이 주제에서 나온 개념 목록

| 개념 | 한 줄 설명 | 다룬 프롬프트 |
|---|---|---|
| 동기(synchronous) | 앞 작업이 끝나야 다음 줄 실행 | ② |
| 비동기(asynchronous) | 기다리는 동안 다른 작업 가능 | ② |
| Promise / async·await | 비동기 작업을 다루는 문법 | ②⑤ |
| localStorage | 브라우저 안 동기 키-값 저장소 | ③ |
| 네트워크 요청 / fetch | 서버와 데이터 주고받기 (비동기) | ④ |
| 동기 API vs 비동기 API | 함수 설계 선택과 파급 효과 | ⑤ |
| Supabase / BaaS | 서버·인증·DB를 묶은 서비스 | ⑥ |
| 로컬 우선(local-first) | 로컬에 먼저 쓰고, 서버는 백그라운드 동기화 | ⑦ |
| 낙관적 업데이트 | 서버 응답 전에 화면 먼저 바꾸는 기법 | ⑦ |
| 동기화 계층 분리 | storage.js(로컬)와 sync.js(서버)를 나눔 | ⑧ |
| 변경 큐(change queue) | 오프라인 중 작업을 쌓아뒀다가 나중에 전송 | ⑧ |
| updated_at / deleted_at | 충돌 해결과 삭제 전파를 위한 필드 | ⑨ |
| soft delete | 삭제를 표시만 하고 실제로 지우지 않음 | ⑨ |
| Last Write Wins | 타임스탬프 기준 충돌 해결 | ⑨ |
| CRDT | 충돌 없이 병합 가능한 데이터 구조 | ⑨ |
